### 실제 코드에서 확인한 것

#### 뉴스 도구의 정보 흐름

대상: [search_news.py](../../src/agent/tools/search_news.py)

```text
coin_code
  → _search_cryptopanic / _search_serpapi
  → 기사 목록: list[dict], 각 항목에 title / url / source
  → lines에 제목·매체 문자열 append
  → "\n".join(lines)
  → 최종 반환은 str: 뉴스 개수 + 제목 + 매체
```

- `source`는 매체 이름이다. 기사 본문이 아니다.
- 공급자별 함수가 받아온 URL은 최종 문자열에서 제외된다.
- 본문·기사 발행 시각은 현재 결과에 포함되지 않는다. 기사 URL을 열어 본문을 수집하는 단계도 없다.
- API 키 미설정·공급자 오류·정상 빈 결과가 최종적으로 같은 “관련 뉴스 없음” 메시지로 합쳐진다.
- [news_agent.py](../../src/agent/news_agent.py)는 이 도구의 반환 문자열을 LLM에 전달한다.

### 학습에서 논의한 설계 원칙

- 모델: 기사 의미·사건 관련성, 부족한 근거와 추가 검색 내용을 판단.
- 코드: 검색 횟수 등 실행 한도를 강제. 판단 과정에도 검증 가능한 규칙은 코드로 확인.
- 충분한 근거 확보뿐 아니라 조사 한도 도달도 종료 조건이다.
- “검색은 했지만 관련 기사를 못 찾음”과 “검색 API 실패”, “관련 기사가 존재하지 않음”은 다른 주장이다.
- 기사 발행 시각과 실제 사건 발생 시각을 구분한다. 시간적으로 앞선 보도 하나로 원인을 확정하지 않는다.
- 보고서는 확인한 사실, 원인 후보, 미확인 사항을 구분한다.
- 본문을 가져오는 도구와 본문을 해석하는 LLM은 역할이 다르다. LLM 연결만으로 URL을 읽을 수 있는 것은 아니다.

이 원칙을 대화에서 다뤘다는 사실과 사용자가 독립적으로 적용할 수 있다는 평가는 구분한다.
항목별 학습 근거는 이 문서 앞부분에 기록했다.

### 아직 정하지 않은 것

1. 검색과 본문 읽기를 한 도구로 묶을지, 별도 도구로 나눌지.
2. 본문 확보 방식: 제공 API / HTTP와 HTML 추출 / 브라우저 중 무엇이 필요한지.
3. 본문 전체와 관련 발췌 중 무엇을 모델에 전달할지, 길이 한도를 어떻게 둘지.
4. 기사 ID·URL·시각·본문·조회 상태를 담을 구체적인 입출력 스키마.
5. 추가 검색의 시작·종료 기준과 횟수·시간·비용 한도.
6. 첫 구현 범위와 검증 사례. 현재의 우선 학습 대상은 뉴스 도구이며 전체 루프 구현은 미정.

## 1. 목표와 범위

기존 자동 리포트가 어떤 자료를 보고 판단했는지 추적하고, 자료 부족·조회 실패를 정확히 표현하도록 개선한다.
그 기반 위에서 필요한 추가 조사와 품질 평가를 진행하고, 이후 대시보드 대화형 기능으로 확장한다.

- 현재 사용자는 책을 읽으며 프로젝트에 적용하고 있다. 읽은 내용을 실제 문제와 연결하고 작은 변경을 검증한다.
- 자동 리포트의 Market/News/Report 흐름을 기본 구조로 유지한다. 자율성이 필요한 부분만 별도로 검토한다.
- 평가는 후속 목표다. 첫 구현을 대규모 평가셋 제작 때문에 미루지 않되 변경 전후를 나중에 비교할 수 있도록 버전·검증 근거를 남긴다.
- 대시보드 챗봇은 후속 확장이다. 이번 첫 작업에는 UI·대화 메모리·자율 검색 루프를 포함하지 않는다.
- 코드가 실행된 것, 단위 테스트 통과, 실제 LLM 품질 개선을 서로 다른 결과로 기록한다.

이 문서는 전체 설계·진행 관리 문서다. 모든 단계의 세부 구현 계획을 미리 확정하지 않는다.
R1 상세 설계를 검토한 뒤 R1만 구현 계획으로 구체화한다. R2 이후의 기술 선택은 각 단계 착수 시 정한다.

## 4. R1 — 뉴스 도구 반환 개선 상세 설계

**설계 상태: 2026-10-02 사용자 최종 승인(“ㅇㅋ 좋아.”). 기사 0건 처리는 사용자 결정, 공급자 응답 해석·보안 보강과 일반 웹 검색 제외는 검토 제안을 승인받음.
구현 순서·코드·검증 명령은 [R1-PLAN.md](R1-PLAN.md)에 있다. 2026-10-06 구현·검증 완료(아래 검증 결과).**

### 해결할 문제

현재 [search_news.py](../../src/agent/tools/search_news.py)는 공급자에서 `title/url/source`를 받고도
최종 문자열에는 제목·매체만 남긴다. 키 미설정, 조회 오류, 정상 빈 결과는 같은 “관련 뉴스 없음” 메시지가 된다.
[news_agent.py](../../src/agent/news_agent.py)는 이 문자열을 LLM에 전달한다.

2026-10-02 검토에서 함께 확인한 문제:

- 조회 실패 로그가 예외 메시지를 그대로 남긴다. `requests`의 연결·HTTP 오류 메시지에는 쿼리 문자열의 API 키가 들어 있다.
- 뉴스 노드의 실패 fallback이 예외 원문을 `headlines`에 넣고, 이 값이 `incidents.agent_report`에 저장된다.
- 기사가 없어도 LLM을 호출한다. 이때 결과는 프롬프트 규칙(NEUTRAL·0.0)으로 이미 정해져 있다.

### 변경 후 데이터 흐름

```text
coin_code
  → 공급자 순서대로 조회: CryptoPanic → SerpAPI(Google News)
      · 키 없음: 요청하지 않고 unavailable 기록
      · 공급자별 규칙으로 응답 해석·항목 검증 → ok / empty / error 기록
      · 검증된 기사가 1건 이상이면 다음 공급자를 호출하지 않음
  → NewsSearchResult: status + articles + attempts
  → news_analyst_node
      · status != ok: LLM 미호출, 규칙으로 NewsEvidence 생성
      · status == ok: 기사 목록을 JSON으로 직렬화해 LLM 입력에 제공
  → 기존 NewsEvidence 반환
```

공급자 선택 순서와 최초 유효 기사 목록을 채택하는 정책은 유지한다.
결과 병합·공급자 추가·모델의 도구 선택은 이 단계에 추가하지 않는다.

### 반환 계약

도구는 Pydantic으로 검증한 `NewsSearchResult` 객체를 반환한다. `@tool`로 감싼 함수도 `invoke(dict)`는 객체를 그대로 반환한다
(langchain-core 1.4.8에서 확인). 모델 도구 호출 메시지에 연결할 때의 직렬화는 R4에서 다룬다.

| 객체 | 필드 | 규칙 |
|---|---|---|
| NewsArticle | `title`, `url`, `source` | 제목·URL은 앞뒤 공백 제거 후 필수. `url`은 공급자가 준 기사 링크에서 앞뒤 공백만 제거하고 나머지는 원래 문자열 그대로 보존하며 `http(s)://호스트` 형식만 검사. 링크한 페이지는 요청하지 않음. 매체를 모르면 빈 문자열 |
| NewsProviderAttempt | `provider`, `status`, `error_code` | 공급자 식별자(`cryptopanic`, `serpapi`), 공급자 상태(`ok / empty / error / unavailable`), `status`가 `error`일 때만 오류 분류이고 그 외에는 null |
| NewsSearchResult | `status`, `articles`, `attempts` | 전체 상태, 채택한 기사 목록(최대 5건), 확인한 공급자의 시도를 순서대로 보존. `ok`면 기사 1건 이상, 그 외 상태는 빈 목록 |

- Pydantic `HttpUrl`은 끝에 `/`를 붙이고 비ASCII·공백을 퍼센트 인코딩하며 호스트를 소문자로 바꾼다. 보존이 목적이므로 사용하지 않는다.
- 키가 없어 요청하지 않은 공급자는 `unavailable` 시도로 기록한다. 앞선 성공으로 확인하지 않은 공급자는 기록하지 않는다.
- 본문·날짜는 수집하지 않는다. SerpAPI가 제공하는 `date`·`published_at`·`snippet`도 R2에서 검토한다.
  기사 필드를 임의로 채우거나 모델이 다시 생성하게 하지 않는다.

### 공급자 응답 해석

| 공급자 | `ok` | `empty` | `error` |
|---|---|---|---|
| CryptoPanic | `results`에 검증된 기사 1건 이상 | `results`가 빈 목록 | HTTP 오류, `results` 누락·목록 아님, 항목 전부 무효 |
| SerpAPI | `search_metadata.status`가 `Success`이고 `news_results`에 검증된 기사 1건 이상 | `search_metadata.status`가 `Success`이고 `news_results`가 없거나 빈 목록 | HTTP 오류, `Success`가 아니거나 없는 상태, 항목 전부 무효 |

- SerpAPI는 결과가 없을 때 HTTP 200과 함께 `error: "Google hasn't returned any results for this query."`를 반환한다.
  `error` 키가 있다는 이유만으로 오류로 판정하지 않는다. `search_metadata.status`를 먼저 확인한 뒤 `news_results`를 해석한다.
- 항목 단위로 검증한다. 제목·URL이 없거나 URL 형식이 맞지 않는 항목은 제외하고 나머지를 채택한다.
  응답에 항목이 있었는데 모두 무효면 `invalid_response` 오류로 처리하고 폴백한다. 제외한 건수는 로그에 남긴다.
- 기사 수 제한(5건)은 검증을 통과한 항목에 적용한다.

| `error_code` | 조건 |
|---|---|
| `timeout` | `requests.Timeout`(`ConnectTimeout` 포함) |
| `http_error` | 2xx가 아닌 응답. 401 키 오류, 429 한도 초과 등 |
| `invalid_response` | JSON 해석 실패, 기대 구조 불일치, 공급자의 실패 상태, 항목 전부 무효 |
| `request_error` | 그 밖의 `requests.RequestException`. 연결 실패 등 |

- `ConnectTimeout`은 `Timeout`이면서 `ConnectionError`이고, `requests.JSONDecodeError`는 `RequestException`의 하위 클래스다.
  `Timeout`을 먼저 분류하고 JSON 해석은 요청 예외 처리와 분리한다.
- 로그에는 공급자·상태·오류 분류·HTTP 상태 코드·제외 건수만 남긴다. 예외 메시지·응답 원문·요청 URL은 반환하거나 기록하지 않는다.
- 위 분류에 해당하지 않는 예상 밖 예외는 도구에서 숨기지 않는다. 뉴스 노드의 실패 fallback이 처리한다.

### 상태 판정

| 조건 | 전체 status | articles |
|---|---|---|
| 어느 공급자든 검증된 기사를 반환 | `ok` | 채택한 목록 |
| 기사 없음, 조회 오류가 하나라도 발생 | `error` | 빈 목록 |
| 기사 없음, 오류 없이 한 공급자 이상 정상 빈 결과 반환 | `empty` | 빈 목록 |
| 모든 공급자 키 미설정 | `unavailable` | 빈 목록 |

우선순위는 `ok > error > empty > unavailable`이다.
예: 첫 공급자 오류 + 두 번째 성공은 `ok`이며 첫 오류는 `attempts`에 남는다.
첫 공급자 정상 빈 결과 + 두 번째 오류는 보수적으로 `error`다. 일부 검색을 끝내지 못한 상황을 정상적인 빈 결과로 표현하지 않는다.
첫 공급자 정상 빈 결과 + 두 번째 키 미설정은 `empty`이며, 사용 불가였던 공급자도 `attempts`로 확인할 수 있다.
`empty`는 조회한 공급자에서 못 찾았다는 뜻이지, 관련 뉴스가 세상에 없다는 뜻이 아니다.

### 뉴스 노드 연결과 변경 경계

2026-10-02 사용자 결정: 기사가 0건이면 LLM을 호출하지 않고 코드가 결과를 정한다.

| 도구 status | LLM 호출 | NewsEvidence |
|---|---|---|
| `ok` | 호출 | 기사 목록 JSON(`title`·`url`·`source`)을 입력으로 모델이 생성 |
| `error` | 미호출 | `headlines=["[ERROR] 뉴스 조회 실패"]`, `NEUTRAL`, `0.0`, `unknown` |
| `empty`, `unavailable` | 미호출 | `headlines=[]`, `NEUTRAL`, `0.0`, `unknown` |
| 노드 실행 중 예외(LLM 실패 등) | — | `headlines=["[ERROR] 뉴스 분석 실패"]`, `NEUTRAL`, `0.0`, `unknown`. 예외 원문은 넣지 않음 |

- 기사가 없으면 모델이 분석할 자료가 없고 결과가 규칙으로 정해지므로 코드가 결정한다. 해당 사건의 LLM 호출 비용과 출력 변동이 없어진다.
- `error`는 시장·리포트 노드 fallback과 같은 `[ERROR]` 표기를 재사용해 리포트 입력에서 “뉴스 없음”과 “조회 실패”를 구분한다.
  리포트 프롬프트는 수정하지 않는다. 실제 모델이 이 표기를 실패로 해석하는지는 R1에서 검증하지 않는다.
- `headlines`를 상태 표시로 빌려 쓰는 임시 방식이며 R3의 분석 상태 필드가 생기면 교체한다.
  `empty`와 `unavailable`은 R1의 `NewsEvidence`에서 구분되지 않으며 리포트 수준의 구분은 R3에서 한다.
- `ok`일 때 뉴스 검색 결과 자리에는 Python 객체의 문자열 표현이 아니라 기사 목록의 JSON 직렬화를 넣는다.
  코인·앙상블 지표 입력은 기존과 같다. 이때 전체 상태는 항상 `ok`이므로 상태·시도 이력은 모델 입력에 넣지 않고 로그로 남긴다.
- 뉴스 프롬프트는 입력 JSON 필드의 의미를 설명하고, 코드가 맡게 된 “뉴스가 없으면 …” 규칙을 제거한다.
  기존 `NewsEvidence` 구조와 structured output 강제는 유지한다.
- 이 단계의 URL 보존 범위는 **검색 도구→뉴스 노드의 모델 입력**까지다. 최종 보고서·DB·UI의 출처 및 분석 상태 보존은 R3에서 해결한다.

  게시물의 `url`은 CryptoPanic 페이지, 원문 링크는 `original_url`이다(공식 문서 페이지 내용은 확인하지 못함).
  프로젝트 키도 비어 있어 실제로는 항상 `unavailable`이며 SerpAPI만 동작한다.
  유료 키 없이 검증할 수 없어 R1에서는 v2로 이전하지 않는다. 재검토 조건: 유료 키 확보 또는 R2 착수 시 공급자 재선정.
- **뉴스 0건 시 일반 웹 검색**(2026-10-02 사용자 제안, R4 후보). `empty`는 “조회한 곳에 없음”일 뿐이므로 더 넓게 찾는 방향은 타당하고,
  거래소 공지처럼 뉴스 검색에 잡히지 않는 공식 자료를 찾을 가능성도 있다. R1에 넣지 않는 이유는 다음과 같다.
  같은 SerpAPI 키로 검색하면 `error`(키 오류·한도 초과)와 `unavailable`은 구제하지 못하고 `empty`만 구제한다.
  웹 결과에는 시세 페이지·오래된 글이 섞이고 날짜가 없을 수 있어 근거 없는 단정 위험이 커지므로 결과 종류·시각 처리(R2)가 먼저 필요하다.
  추가 검색의 효과·비용은 R4에서 비교하기로 했다. 재검토 조건: R1 이후 시도 로그에서 SerpAPI `empty`가 자주 확인되면 R2 착수 때 앞당겨 검토한다.
- `scratch/test_all_structured.py`는 `search_news`를 문자열 스텁으로 교체하므로 R1 이후 뉴스 노드에서 동작하지 않는다. 미추적 실험 파일이라 수정하지 않는다.
- 시장·리포트 노드의 fallback도 예외 원문을 저장한다. 분석 상태를 다루는 R3에서 함께 정리한다.
- R1 이전 코드는 SerpAPI 401·429·연결 실패 때 키가 담긴 요청 URL을 로그에 남겼다(비교 스크립트 3·4번). 그 시기의 로그를 저장하거나 공유했다면 키 교체를 검토한다.
- 루트 로거를 DEBUG로 설정하면 `urllib3`가 키가 담긴 요청 URL을 기록할 수 있다. 현재 `src/`에는 그런 설정이 없다.
- 실제 HTTP 차단 fixture는 `tests/test_agent_tools.py`에만 있다. 저장소 전체 `tests/conftest.py`로 넓히는 것은 R1 범위 밖 후보다.

## 6. R3 — 기존 리포트 개선

**목표:** 사용자가 보고서의 주장과 원본 근거를 확인하고 부분 분석과 실패를 구분할 수 있게 한다.

- 선행 조건: R1·R2에서 출처·본문·시각·획득 상태를 제공함.
- 근거 ID로 기사·시장 자료를 보존하고, 뉴스 분석→종합 보고서→DB→리포트 화면에 연결한다.
- `success / partial / failed / skipped` 등 분석 상태를 코드에서 결정하고 획득 상태와 분리한다.
  현재 실패 fallback도 `analyzed`로 저장할 수 있는 경로를 이 단계에서 고친다.
  시장·리포트 노드 fallback의 예외 원문 저장과 R1의 임시 `[ERROR]` headlines 표기도 분석 상태 필드로 교체한다.
- 사실·원인 후보·미확인 사항을 구분하고 자료 부족 시 판단 보류가 가능하도록 출력 계약을 설계한다.
- Replay의 사건 기준 시각 누락, 시장 조회의 `now()` 사용, legacy 지표명 라우팅 불일치를 정리한다.
- 완료 기준: 근거 링크를 추적할 수 있음, 기사/시장 근거가 없으면 임의 출처를 만들지 않음,
  부분·실패 상태가 저장과 화면에 일치함, 과거 사건에 현재 시장 자료가 섞이지 않음.
  당시 뉴스가 없으면 재현 불가 범위를 명시하며 기존 저장 리포트도 읽을 수 있음.
- 검증: 상태·근거 검증 단위 테스트, 저장 통합 테스트, 리포트 목록/상세의 주요 사용자 흐름 확인.

## 7. R4 — 추가 조사와 품질 평가

**목표:** 추가 도구 호출이 분석에 실제로 도움이 되는지 비용과 함께 측정하고 도입 여부를 정한다.

- 선행 조건: R3에서 결과·근거·상태를 추적할 수 있음. 평가셋 구축은 현재 R1의 선행 과제가 아니다.
- 고정된 사건·검색 결과·기사와 기대 행동으로 작은 평가셋을 구성한다. 수정용 사례와 최종 비교용 사례를 분리한다.
- 비교 대상: 기존 제목 입력 버전, 근거를 보강한 고정 절차, 같은 도구·자료를 쓰는 제한된 모델 도구 선택.
  정보 보강과 자율성 효과를 나눠 보고 모델·자료·판정 기준을 가능한 한 고정한다.
- 후보: 뉴스 0건 시 일반 웹 검색(2026-10-02 사용자 제안). 코드가 정한 고정 규칙판과 모델이 추가 검색을 고르는 판을 비교 대상에 포함할 수 있다.
  R1에서 제외한 이유와 재검토 조건은 R1의 범위 밖 후보에 기록했다.
- 최초 구현 전후의 소스 버전·입출력 계약을 기록해 기존 버전을 이후에도 재현할 수 있게 한다.

  근거 적합률을 쓸 때 근거 미선택은 N/A로 두고 답변 보류·사례 성공 여부와 함께 본다.

- 완료 기준: 동일 조건의 전후 결과와 실패 사례·사례 수·반복 실행·비용을 보고하고, 루프 도입/수정/보류를 결정함.

- 첫 후보는 “이 보고서 설명해 줘”, “근거 기사 보여 줘”처럼 저장된 보고서·근거를 활용하는 질문이다.
- 질문에 따라 추가 검색·조회가 필요할 때 기존 도구를 재사용하는 대화형 에이전트를 검토한다.
- 착수 시 선택: 실제 사용자 질문, 리포트 접근 범위, 세션 상태, 비용 한도, 새 조사 결과와 기존 리포트의 관계.
- 완료 기준: 합의한 질문 흐름에서 출처·분석 한계를 표시하고, 관련 보고서 접근 및 도구 실행을 제한하며 주요 대화 흐름을 검증함.
- 채팅 UI와 자율 실행은 별개다. 챗봇을 만들었다는 이유로 자율 에이전트라고 설명하지 않는다.

# E1 평가셋 (e1-v1)

코드를 바꿀 때마다 같은 사건 10건을 같은 재료로 다시 풀려서 판단 품질을 숫자로 비교하는 시험지.
설계 배경은 [ROADMAP.md §5](../docs/agent-improvement/ROADMAP.md).

## 실행

```bash
uv run python -m evals.run_eval                          # 10건 × 3회, 결과는 evals/results/
uv run python -m evals.run_eval --cases E1-01 --runs 1   # 일부만
DB_HOST=localhost uv run python -m evals.build_cases     # 사례 재생성(DB 읽기 + SerpAPI 사례당 1회)
```

평가 실행은 OpenAI만 부른다. DB 접속과 뉴스 HTTP 요청은 막혀 있어서, 호출되면 노드 실패로 기록된다.

## 사례를 만든 방법

2026-10-07 확인 시 DB `incidents`가 0건이었다(스케줄러 미실행). 그래서 저장된 사건 대신
`agg_1min` 9일치(2026-09-28~10-07, 289개 코인)에 실제 감지기(`EnsembleScorer`, 스케줄러와 같은 가중치)를
과거 시각 기준으로 다시 돌려 사건을 만들었다(`build_cases.py`).

- 백필 결과: 사건 5,173건(30분 넘게 끊기면 새 사건), 하루 약 575건.
- 그중 67%가 수집 공백 구간에서 나왔다(직전 60분 BTC 1분봉이 50개 미만). 지표 4개가 모두 울린 사건 78건 중 75건이 공백 구간이었다.
  노트북 절전으로 수집이 끊긴 뒤 처음 들어온 1분봉이 24시간 평균과 크게 달라 보이는 것으로 추정한다.

| 재료 | 고정 방법 |
|---|---|
| 초기 상태 | 기준 시각까지 1440분 창으로 감지기를 돌린 결과를 `graph.build_initial_state()`로 변환 |
| 시장 스냅샷 | 기준 시각까지 60분 행을 `summarize_market_rows()`로 요약 — `query_market_window`와 같은 문자열 |
| 뉴스 스냅샷 | 운영 `search_news`를 그대로 실행하되 SerpAPI 요청에만 날짜 범위(기준일 전날~당일, KST)를 붙임 |

## 정답 기준 (분석가 기준 v1 — 2026-10-07 사용자 확정)

정답은 모델이 받는 자료(시장 요약·지표·기사 제목)로 뒷받침되는 판단이다. 실제 급등 원인을 확정하는 게 아니다.
프롬프트의 규칙(지표 개수로 결정)은 정답이 아니라 별도 축(rule)으로 잰다.

| `recommended_action` | 기준 |
|---|---|
| MONITOR | 근거 부족(60분 데이터 포인트 30개 미만 또는 거래 30건 미만) 또는 60분 변동 1% 미만 |
| ALERT | 60분 변동 1% 이상 5% 미만 |
| ESCALATE | 60분 변동 5% 이상 |
| (한 단계 올림) | 기사가 공식 악재(해킹·상장폐지·입출금 중단)를 가리킬 때 — v1 사례에는 없음 |

`news_relevant`: 기사 제목이 이 코인의 이 변동을 설명할 수 있으면 true. 기사가 없거나 조회 실패면 null(채점 제외).

## 채점 축 (`scoring.py`)

| 축 | 질문 | 용도 |
|---|---|---|
| judgment | `recommended_action`이 분석가 답과 같은가 | 주 점수 |
| rule | 프롬프트 규칙 답과 같은가 | 지시 준수 보조 지표 |
| news | `relevance_score`를 임계값으로 자른 값이 라벨과 같은가 | R2(기사 본문) 효과 측정용 |
| routing | 실행 노드가 기대 노드와 같은가 | 코드 회귀 확인 |

`confidence`는 맞힌 실행과 틀린 실행의 평균을 나란히 기록만 한다.

## 기준 점수 (2026-10-07, R1 완료 상태)

결과 파일: [`results/20261007T012833Z_b076514.json`](results/20261007T012833Z_b076514.json).
모델 `gpt-5.6-luna`, 커밋 `b076514` + 미커밋 리팩터(`summarize_market_rows`·`build_initial_state` 분리, 동작 동일), 라벨 확정, 10건 × 3회.

| 축 | 3회 범위 | 평균 | 채점 사례 |
|---|---|---|---|
| judgment (분석가 답 일치) | 40%~40% | 40% | 10 |
| rule (프롬프트 규칙 준수) | 90%~100% | 97% | 10 |
| news (관련성 일치) | 50%~62% | 54% | 8 |
| routing | 100%~100% | 100% | 10 |

- `confidence` 평균: 맞힌 실행 0.71, 틀린 실행 0.84 — 틀릴 때 더 확신한다.
- 토큰 130,607(입력 87,131 / 출력 43,476), 그래프 1회당 약 4.4k. 노드 실패 0/30, 평균 13.0초. 단가 미확인이라 비용은 토큰으로만 기록.

### 틀린 사례 노드별 추적 (저장된 노드 출력 기준, LangSmith 전)

| 사례 | 시장 노드 | 뉴스 노드 | 리포트 노드 | 어긋난 곳 |
|---|---|---|---|---|
| E1-10 LIT | +3.87% 상승 추세, conf 0.9 | 다른 코인 기사("0.15달러")에 관련성 0.9 | 그 기사를 원인 근거로 인용, "전 지표 이상"이라 ESCALATE | 뉴스(오귀속) → 리포트(규칙) |
| E1-08 XRP | "거래 5건, 데이터 신뢰도 검증 필요"를 스스로 지적 | 일반 시황 기사에 0.68~0.78 | "표본 왜곡 가능성"을 쓰고도 규칙대로 ESCALATE(3회 중 2회) | 리포트(규칙이 근거를 덮음) |
| E1-01 TRAC | +17% 급등·과열 정확히 서술 | 보유 주소 60개 증가 기사에 0.55~0.58 | "복수 지표"라 ALERT, 기사를 원인으로 인용 | 리포트(규칙) + 뉴스(오귀속) |

정리하면 judgment 오답 18회(6건×3회) 중 17회가 프롬프트 규칙 답과 같다(나머지 1회는 E1-08의 ALERT). 원인은 모델 능력보다 지표 개수 규칙이다.
news 오답은 모두 무관한 기사를 관련 있다고 본 쪽이다(가격·시각 대조 없음). R2(본문·시각)와 R3(판단 규칙·근거 계약)가 각각 겨냥할 지점이다.

## 한계

- 사례 10건, 라벨은 1인 판단. 기준표 경계값(1%·5%·30건)은 임의로 정한 값이다.
- 뉴스 시각은 근사다. Google 날짜 필터가 정확하지 않고 기사 날짜도 "4 days ago" 같은 상대값이라, 사건 뒤에 나온 기사가 섞였을 수 있다.
- 뉴스 검색어가 일반적이라(`{코인} 코인 뉴스`) 변동을 설명하는 기사가 거의 없다. news 축은 대부분 false 라벨이며 "무관한 기사를 원인으로 끌어오지 않는가"를 주로 잰다.
- 기준 시각은 5분 감지 주기 안의 마지막 1분봉으로 근사했다.
- `temperature=0`이어도 출력이 흔들리므로 3회 이상 실행해 범위로 기록한다.
- 스모크 실행(2026-10-07): 그래프 1회당 약 2.7k~4.4k 토큰, 10~15초.
